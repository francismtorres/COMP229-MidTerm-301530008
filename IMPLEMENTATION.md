## 2. Endpoint Checklist

Input validation lives in `middleware/validateItem.ts` and runs before the
controllers, so bad requests get a clear `400` without a database round trip.
Mongoose schema validation in `models/Item.ts` is a second layer (required
fields, enums, min/max lengths, no future dates). The controllers in
`controllers/itemController.ts` handle persistence, ownership and mapping
database errors to status codes.

### GET `/api/items`
- Filters supported: `?type=` (Lost/Found), `?category=` (Electronics/Clothing/Books/Accessories/Other), plus `?status=` (Open/Returned). Filters can be combined.
- Status codes: `200` with an array (newest first, owner name/email populated); `400` if a filter value is not one of the allowed enum values.
- Notes: Public route. Only whitelisted query keys are copied into the Mongo filter, so query-operator injection (e.g. `?type[$ne]=x`) is rejected as a `400`.

### GET `/api/items/mine`
- How you scope to the signed-in user: `requireAuth` verifies the JWT and sets `req.userId`; the query is `Item.find({ owner: req.userId })`.
- Status codes: `200` (array, possibly empty); `401` with no or an invalid token.
- Notes: Declared before `/:id` so `"mine"` is not treated as an id.

### GET `/api/items/:id`
- How you validate `:id`: `validateObjectId` middleware checks it is a 24-character hex ObjectId.
- Status codes (valid id / invalid id / not found): `200` / `400` / `404`.
- Notes: Public route; owner name/email are populated.

### POST `/api/items`
- How you set `owner`: always `req.userId` from the verified JWT. A client-supplied `owner` is rejected with `400`.
- How validation errors are returned: `400 { "error": "Validation failed", "details": [ ...every problem... ] }`. Malformed JSON returns `400 { "error": "Malformed JSON in request body: ..." }`.
- Status codes: `201` created; `400` invalid body; `401` no or invalid token; `409` duplicate title.
- Notes: **Title is the unique field.** The schema has a unique index on `title` with a case-insensitive collation (`{ locale: 'en', strength: 2 }`), so "Black Backpack" and "black backpack" count as duplicates. The controller checks first and returns a friendly `409`; the unique index catches race conditions (E11000 → `409`). Unknown fields are rejected; strings are trimmed.

### PUT `/api/items/:id`
- How you check ownership: load the item, then `item.owner.equals(req.userId)`; otherwise `403`.
- Which fields you allow to be updated: `title`, `description`, `type`, `category`, `location`, `date`, `status` (partial updates allowed). `owner`, `_id` and the timestamps cannot be changed.
- Status codes (invalid id / not found / not owner / success): `400` / `404` / `403` / `200`. Also `401` with no token, `400` for an empty body or invalid values, `409` if the new title belongs to another item.
- Notes: Uses `item.set(updates)` + `item.save()` so the full schema validation runs on update (unlike a plain `findByIdAndUpdate`).

### DELETE `/api/items/mine`
- Query used: `Item.deleteMany({ owner: req.userId })`.
- Response shape (`deletedCount` / `204`): `200 { "message": "Deleted N item(s) owned by <email>", "deletedCount": N }`.
- Notes: Only the caller's items are removed; other users' items are untouched (verified in Postman and MongoDB Compass).

### DELETE `/api/items/:id`
- How you check ownership: same as PUT — load, compare `item.owner` with `req.userId`, `403` if different.
- Status codes: `200 { "message": "Item deleted successfully", "deletedId": ... }`; `400` invalid id; `401` no token; `403` not owner; `404` not found.
- Notes: `200` with a JSON body (rather than `204`) so the deleted id is visible.
